### النطاق والاستضافة وDNS

- **التسجيل:** GoDaddy بحسب إفادة المالك في التكليف؛ لم أتحقق من حساب التسجيل أو RDAP مستقلًا.
- **الموقع المنشور:** واجهته الحالية تحمل علامة GoDaddy Website Builder. هذا دليل على منصة بناء الصفحة؛ لا يثبت تفاصيل الحساب أو الخادم الخلفي.
- **DNS authoritative nameservers وA/AAAA/CNAME/MX/TXT/TTL:** لم أتمكن من جلبها. استعلام DNS من بيئة التنفيذ فشل، وواجهات RDAP/DNS العامة لم تُرجع بيانات قابلة للقراءة. لا أضع أسماء خوادم أو IP تخمينية.
- لا توجد هنا جلسة حساب GoDaddy موثقة أو صلاحية DNS متصلة. قبل الانتقال يلزم تصدير zone أو قراءة إعدادات النطاق من الحساب. لا ترسل كلمة المرور في المحادثة.
- لا يوجد مبرر حالي لنقل تسجيل النطاق أو ملكيته من GoDaddy.

## 2. اتجاه المنتج والنص

Hero النهائي:

> Evidence beyond the system that produced it.
>
> Measure what happened. Preserve how a conclusion was reached. Carry the evidence forward—so others can verify it independently.

الصفحة تعرّف PayGod كبنية قياس ودليل واستدلال وإثبات قابل للحمل، مع تنفيذ حالي موثق يتمحور حول deterministic kernel وdecision evidence. لا نَعِد بمنصة قياس عامة أو محرك استدلال شامل جاهز لكل مجال.

التسلسل: Measurement → Evidence → Inference → Proof → Portable Evidence Bundle → Independent Verification.

الصفحة كاملة في `src/page.html`، والنص المستخرج في `COPY_EN.md`. الأقسام: Hero، المشكلة، ست قدرات أساسية، المعمارية، التحقق وحدوده، Demo تفاعلي، حالات الاستخدام الخمس، CTA.

CTA الأساسي: Verify an evidence bundle. الثانوي: Explore the kernel. لم نضف نموذجًا يزعم الإرسال دون backend أو عنوان مبيعات غير موثق.

## 3. التصميم

- خلفية حبرية داكنة، نص أبيض رمادي، لون أخضر مائي للدليل والتحقق.
- رسم تقني حقيقي: producer → حزمة تتجاوز حدود البيئة → verifier؛ لا صور stock ولا أشكال تدّعي أنها بيانات حية.
- منطقة حدود الثقة بلون فاتح لتكون نقطة توقف بصرية واضحة.
- بطاقات القدرات، مخطط بثلاثة أعمدة، Inspector للدليل، وحالات استخدام في صفوف.
- الإنجليزية أولًا، تخطيط متجاوب، عناصر HTML دلالية، focus مرئي، skip link، reduced motion، وإشعار نتيجة عبر aria-live.
- الرمز الهندسي في المعاينة مقترح بصري جديد، وليس ادعاء بأنه شعار علامة معتمد.

## 5. Demo ودليل عمله

1. Load clean bundle ثم Run verification → VALID.
2. Tamper with evidence يغيّر 420 إلى 421 في artifact فقط؛ بايت واحد مختلف → INVALID.
3. Alter receipt يبدل flag إلى allow دون تغيير ledger → INVALID.
4. تعديل JSON يدويًا يلغي النتيجة القديمة حتى إعادة الفحص.
5. استيراد ملف JSON، تصدير النقل، وتنزيل نتيجة machine-readable.

الحزمة تضم measurement.json وledger.jsonl وmanifest.json وreceipt.json. مولّد fixture صريح وليس تشغيلًا مزعومًا للنواة. المخطط المستخدم مفهوم متوافق مع فحوص المتحقق الأصلي، وليس تصريحًا باجتياز كل JSON schema في المستودع.

نجحت الحزمة مع Python v0.2.0 الأصلي. نسخة المتصفح محدودة بالأعداد الصحيحة الآمنة، وتعلن هذا. SHA-256 عبر Web Crypto إن توفر، ومعه fallback مستقل للمعاينة offline تم اختباره مقابل Node crypto. لم يخضع fallback لتدقيق مستقل.

## 6. الاختبارات

- Browser verifier: 8 حالات؛ قبول clean ورفض payload tamper وreceipt substitution وmissing ledger وclock downgrade وmalformed controls وduplicate entry.
- Unicode canonicalization example مطابق لسلوك المرجع؛ floats خارج نطاق Demo وتُرفض.
- SHA-256 fallback: 11 متجهًا مقابل Node crypto، تشمل العربية وUnicode وحدود 55/56/63/64/65 بايت و1 MB.
- تشغيل end-to-end دون Web Crypto: PASS.
- Python المرجعي: 6 حالات مستقلة تشمل clean و5 حالات فشل.
- تحقق UI في المتصفح: clean → VALID؛ تغيير دليل → INVALID؛ لا نتيجة نجاح ثابتة.
- فحص التخطيط عند viewport فعلي 375 بكسل داخل إطار عرض 390 بكسل: scrollWidth=375 وclientWidth=375؛ لا تجاوز أفقي على الصفحة. هذه معاينة بعرض هاتف وليست تجربة Safari/iOS فعلية.
- ليست هذه اختبارات اختراق أو تدقيق تشفيري أو إثبات توافق شامل. حجم المدخلات محدود إلى 2 MB للنقل و1 MB لكل artifact و32 ملفًا.

## 7. خطة النشر المقترحة — لا تنفيذ قبل الاعتماد

أوصي مبدئيًا بـ **Vercel للاستضافة الثابتة، GitHub للمصدر، وبقاء تسجيل GoDaddy وDNS الحالي**. السبب: الموقع لا يحتاج backend، ويمكن تغيير سجلات الموقع فقط دون نقل التسجيل أو نقل nameservers. Cloudflare Pages بديل جيد، لكن ربط apex عليه عادة يتطلب نقل nameservers إلى Cloudflare؛ لا نحتاج توسيع التغيير الآن.

مراجع رسمية راجعتها:
- https://vercel.com/docs/domains/working-with-domains/add-a-domain
- https://developers.cloudflare.com/pages/configuration/custom-domains/

هذا اقتراح بنية، وليس تأكيدًا أن حساب استضافة مدفوع متاح أو أن إعداداته الحالية معروفة. مراجعة خطة الاستخدام التجاري والسعر تكون عند اختيار الحساب، دون اشتراك تلقائي.

### تسلسل التنفيذ بعد الموافقة

1. اعتماد هذا commit والنص والتصميم ونطاق demo.
2. قراءة إعدادات النطاق الفعلية وتصدير DNS بالكامل؛ تسجيل قيم rollback الأصلية وTTL وحالة البريد وDNSSEC/CAA إن وجدت.
3. إنشاء مشروع استضافة مستقل مرتبط بالمصدر المعتمد؛ root directory = website، output = dist؛ الكود المبني موجود بالفعل. لا تُوصل فرعًا تجريبيًا بالإنتاج تلقائيًا.
4. معاينة HTTPS منفصلة محمية إن أمكن؛ اختبار الهاتف الحقيقي وSafari، الروابط والتنزيلات وعدم إرسال بيانات الأدلة للخادم.
5. تهيئة domain في مشروع الاستضافة دون قطع الحالي. استخراج قيم A/CNAME الدقيقة من شاشة المشروع، مع فحص تعارض AAAA وأي redirect قائم.
6. تقديم جدول DNS حقيقي: الاسم، النوع، القيمة السابقة، القيمة الجديدة، TTL، سبب التغيير. لا توجد قيم افتراضية مخمّنة هنا.
7. طلب اعتماد جدول DNS وتوقيت القطع، ثم تغيير سجلات الموقع فقط. الحفاظ على MX وSPF وDKIM وDMARC وسائر TXT وNS.
8. HTTPS وwww/apex canonical redirect، فحص الأداء والوصول، إزالة noindex من النسخة الإنتاجية وإضافة canonical URL. إبقاء noindex على المعاينات.
9. إبقاء GoDaddy Website Builder ونسخته القديمة حتى اجتياز التحقق بعد التحويل. لا إلغاء اشتراك تلقائي.
10. rollback: إعادة قيم DNS الأصلية الموثقة ثم إعادة إصدار الاستضافة السابق إن لزم. زمن الرجوع متأثر بذاكرة DNS وTTL؛ ليس فوريًا مضمونًا.

### ضوابط نسخة الإنتاج

قبل النشر العام، أضف CSP يتضمن بصمة script/style أو انقلهما إلى ملفات same-origin مع سياسة مناسبة؛ استخدم X-Content-Type-Options وReferrer-Policy وPermissions-Policy. لا حاجة لتحليلات أو ملفات ارتباط لهذه النسخة. لا يوجد نموذج إرسال بيانات أو backend وهمي. راجع ملكية العلامة والنص والروابط؛ لا شهادات أو أسماء عملاء أو ضمانات SLA غير مثبتة.

## 8. قرار الاعتماد المطلوب لاحقًا

المطلوب الآن مراجعة التصميم والنص والـDemo. لا يمثل اعتماد المظهر موافقة ضمنية على تعديل DNS. البيانات الوحيدة الناقصة لإغلاق تدقيق البنية الحالية هي zone/settings الفعلية وحساب الاستضافة المختار. أُنجزت النسخة القابلة للمراجعة دون انتظارها.
